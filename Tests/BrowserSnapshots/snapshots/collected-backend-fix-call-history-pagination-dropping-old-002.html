      Summary

      Web call history was capping at roughly the first page (looked like "last 3 days") because the pagination cursor in GetNotesListView was keyed on each note's updated_at, while the underlying DB query sorts and filters by created_at:

      • [redacted-token] — candidate cursor used item.UpdatedAt
      • [redacted-token] (and voice memo / capture repos) — Sort(CreatedAt, ID) + created_at < before

      When older calls were bulk-touched (transcription backfill, CustomerIO/contact-score sync, etc.), their updated_at got bumped above the page-1 cursor. The next page's in-memory filter then dropped every candidate whose updated_at >= cursor, returning an empty page → the web stopped paginating. Data-dependent: only users whose old calls were re-written hit it. Topics were unaffected because their cursor (last_active_at) already matches the DB ordering column.

      Fix: align the candidate cursor key with the DB-sort column. For calls, voice memos, and captures, the cursor candidate now stores created_at instead of updated_at. No proto, repo, or display changes.

      Test plan

      • Regression test added: [redacted-token] — creates 3 calls 24/48/72h old with the two older ones' updated_at bumped to "recent", then paginates with limit=2 and verifies the oldest call still surfaces on page 2 (would return empty before the fix).
      • ./tma local code validate
      • Manual: in the web app, scroll the call history past the first page for a user with historical calls; older items continue to load instead of capping.

      Reported in Slack as USR-651 (Triage Bot).

      Fixes USR-651: notes/call history infinite scroll could stop after the first page when older items had updated_at bumped (transcription backfill, sync jobs) while repos still order and filter on created_at.
